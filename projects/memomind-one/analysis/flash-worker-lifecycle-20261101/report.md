# Dedicated native flash-worker lifecycle

**A one-shot worker is the smaller first canary design.** It must receive an independent owned operation context, not a pointer to the current graphics owner, and remain discoverable after screen deletion. The newly authorized [256-byte explicit heap carve](heap-carve-review.md) supplies that stable registry if both witnessed startup/table edits are integrated. This report is read-only native/source analysis; it does not implement or admit device writes.

Native source is stock H001Y1.0.3.127 app body SHA256 `81346c77371a91544dd0b79dd7f108f553f60d5459a3e7e797ebffbebbda5ba8`. Existing runtime source paths were read as working-tree snapshots, not changed. New Ghidra exports used readOnly/noanalysis. The evidence and uncertainties below are independent of the fact that ordinary stock task creation is widely used.

## Actual native task contract

```c
void *task_create(void (*entry)(void *), void *arg,
                  uint32_t priority, uint32_t stack_words, const char *name);
// 0200f168
```

[0200f168](../ghidra/input-adapter/function-0200f168.c) allocates a12-byte wrapper through generic allocator02009904. Layout: native TCB pointer+0, callback+4, argument+8. It searches the native name/priority table with a16-byte comparison and may override priority. A zero stack argument becomes0x200; it passes only the low16bits of stack_words to the scheduler. Reject zero/out-of-range sizes at the custom boundary instead of relying on truncation/default behavior. Use an immutable unique name at most15characters plus NUL; do not borrow "plugin_flash" or assume requested priority necessarily wins against arbitrary runtime table contents.

Creation suspends scheduling through [020088a6](native/function-020088a6.c), calls0200c4f2, stores the returned TCB and registers the wrapper as task tag atTCB+50 via [0200c1b4](native/function-0200c1b4.c), then resumes scheduling through [02008a52](native/function-02008a52.c). Resume drains pending-ready work/ticks and can request a context switch. Consequently the new task may run before task_create returns. A one-shot task may even have finished and freed its wrapper. The returned pointer is usable as a success/nonzero indication, **not a durable job pointer, join handle, or proof the task is still alive**. Initialize and publish all job/registry ownership before calling create; do not make the worker wait for fields that the creator plans to fill afterward.

[0200c4f2](../ghidra/display-adapter/timer/function-0200c4f2.c) allocates stack_words*4bytes, then a124-byte TCB. Stock plugin_flash passes0x800words, therefore8192bytes. It fills the stack witha5, sets metadata/list state and priority (clamped to14), initializes the saved frame, and inserts the task into native ready lists. These allocations are additional to the12-byte wrapper and the CFW job/buffers; allocator metadata adds further overhead.

The native frame initializer is [02009060](native/function-02009060.asm). Core creation computes initial top `(stack_base+4*words-4)&~7` at0200c540..0200c548. Initializer reserves248bytes; restored context adds128+120bytes before mret. Entry stack is therefore **only guaranteed8-byte alignment**, and native trampoline0200f142 subtracts16 without strengthening it. An appended GCC C worker needs an assembly entry veneer that saves original SP/RA, aligns SP down to16, reserves an aligned save frame, calls C, restores the original SP/RA, and returns. Test incoming SP modulo16 both0 and8. This is distinct from existing hook tests that begin with aligned stack.

The [native context instructions](../ghidra/input-adapter/task-context.asm) do not save/restore gp or tp: native tasks share the established gp02011688 and leave tp untouched. Do not install an extension gp, TLS base, or alternate tp. Preserve the native integer ABI/callee-saved state. Startup/task frame evidence supports FP-enabled tasks and32 saved FPRs, but does not establish fcsr isolation; an integer-only canary avoids adding that dependency. [FP context limits](../ghidra/input-adapter/fpu-context.md) remain applicable.

## Return, failure and deferred reclamation

[Trampoline0200f142](../ghidra/external-xip-review/native/function-0200f142.asm) calls callback(argument), then frees the12-byte wrapper and invokes task-delete0200c7d2(0). It does **not** free the argument. A CFW one-shot callback should return normally after releasing its owned transient buffers and publishing its final state; it must not separately free the native wrapper or force-delete its own handle.

[Self-delete0200c7d2](native/function-0200c7d2.c) removes the current task from lists and places it on the termination list0205cce0. [Idle reaper0200cb12](reaper/function-0200cb12.c) later removes it and frees stack+TCB. A published DONE state means the CFW operation finished its owned work, not that native stack/TCB memory has already been reclaimed. No task-join contract was established. Repeated create/finish cycles can accumulate unreaped task storage if idle does not run. A once-per-boot canary avoids depending on rapid repeated reclamation.

If stack allocation fails, native creation returns-1; if TCB allocation fails it frees the allocated stack first. The outer wrapper frees its wrapper and returnsNULL on scheduler-create failure. However [0200d8ce](native/function-0200d8ce.c) calls generic02009904, and that allocator invokes the configured OOM hook on failure. [Allocator evidence](../ghidra/display-adapter/report.md) shows startup registering the assertion-producing OOM policy. Thus three allocations—wrapper, stack, TCB—can assert before these NULL cleanup branches are reached. Total free bytes are a snapshot, not a largest-block/concurrency guarantee. A successful CFW try-allocation does not reserve a native stack block, and allocating/freeing a probe does not guarantee later creation.

Use ordinary-task creation only with a deliberately small bounded task/buffer budget and explicit headroom policy; record this remaining native OOM risk. Do not surround task creation with IRQ-disabled or scheduler-suspended custom regions to fake an atomic reservation, suppress the OOM hook, forge a TCB, or manually supply a synthetic scheduler frame. Static task creation/preallocated stack APIs were not proved in this pass. The existing persistent registry does not itself resolve native allocation failure policy.

## Current graphics ownership is unsuitable as worker lifetime

`runtime/graphics/graphics.c` stores an owner in a native LVGL child DELETE callback. `find_owner` enumerates the current screen's child callback records. Its20ms timer deletes the owner on launcher/screen change or1000ms lease expiration. DELETE immediately clears magic, deletes timer, disposes the scene, invalidates image cache, frees pixel data, and frees the owner. `scene_session_dispose` releases the scene/store state. None is a worker join or cancellation handshake.

Therefore a worker must not retain owner*, scene*, pixel pointers, original TLVs, an envelope pointer, or any temporary handler buffer. The stock display worker frees its envelope after dispatch. Graphics post copies bytes synchronously but may silently drop the envelope; return from post is not evidence a worker started or completed. Existing scene callbacks are deliberately display-task-only and must not be invoked from the flash worker.

A two-reference heap job (owner+worker) could prevent a UAF after DELETE, but would not solve discoverability: a deleted child disappears, and a new owner could admit a second transaction while the old worker is still restoring its sector. The explicitly reserved registry resolves that specific gap. It has a lifetime through normal boot independently of screens, while any registry-held heap pointer retains ordinary ownership. Do not repurpose CUS8 singleton02011e48 or native queue/task slots.

## Recommended one-shot flow with explicit registry

The following is a proposed interface/lifetime design, not existing firmware behavior:

1. The fixed-profile command validates exact operation/sector/token and copies bounded input into owned memory. Under a short native critical section, the registry transitions from unused to PREPARING with nonce/generation. Reject other starts for the rest of this boot, including after screen deletion, host timeout, or ambiguous task-create completion. No raw addresses or registry pointers come from the wire.
2. Allocate the needed operation buffers through the proven try allocator, with fixed bounds. Publish the fully initialized context pointer and a start state before create. The worker argument may be the fixed registry address or a separately owned context whose lifetime is registry-owned. The creator retains no assumption that the task is still pending after task_create returns.
3. Create the normal task through the alignment veneer. On a clean NULL return, record launch failure and release context/buffers exactly once; do not claim flash execution. A nonzero create result is admission only. The returned wrapper is neither retained nor dereferenced. Fixed registry remains queryable even if no UI owner exists.
4. Worker is the only mutator of its private operation buffer and performs native read/erase/program/readback/cache sequence outside all custom critical sections and outside display/observer/ISR context. An ordinary driver call has unbounded busy polling; a host timeout is not cancellation. If an operation already changed flash, UI loss must not bypass the required restore/verification steps. Cancellation, if supported, is only a request checked at safe operation boundaries under a defined restoration policy.
5. Worker writes a bounded final result into the registry, atomically publishes completion under the short critical section, clears/releases its owned heap pointers in an agreed order, then returns. No worker code may touch a freed context after publication permits another task to release it. Prefer fixed inline scalar result plus hashes/provenance over a borrowed reply pointer. Registry state remains terminal/once-used for this boot, preventing overlap even while native task cleanup is pending.
6. Host polls a read-only status command. A BT/display handler copies a small registry snapshot under critical, releases critical, then allocates/serializes/sends using existing correlated GM response APIs. Never call JSON/TLV allocation or send inside critical. Replies contain nonce/generation and phase, so a stale event or reconnect cannot be mistaken for completion. A send/drop failure does not erase the retained result. If routed through the display queue, absence of a response remains timeout; a direct bounded BT snapshot avoids depending on screen ownership. No flash work runs in that handler.

The fixed registry can be initialized once after boot-clear with an ABI/version/magic published last. Every profile using it must contain both heap/BSS edits. Its zero state is volatile reset state, not a flash recovery record. A reset during mutation destroys the registry and requires independent durable transaction/backup recovery rules.

Critical pair [0200a23a/0200a264](followup/function-0200a23a.c) saves/disables/restores MIE and nests; use it only for bounded scalar pointer/state/result publication with appropriate compiler ordering. It does not establish cross-core synchronization. Do not hold it while copying a sector, allocating, creating/deleting a task, waiting, logging, interacting with LVGL, or calling the native flash wrapper (which acquires its own lock).

## Persistent worker for full scene storage

A persistent worker is appropriate when repeated operations justify one retained stack/TCB and a bounded command queue or mailbox. Its stable registry must own worker/context/queue independently of any scene. Commands carry owned bounded copies and explicit generations; scene teardown invalidates that scene generation, not the worker's in-flight native operation. Completion records contain no borrowed owner pointer. Display resolves its own live owner and matching generation before presenting a completion, while storage status remains queryable without the owner.

The native ordinary queue API is concrete: create0200ee6a forwards `(depth,item_bytes,0)` to native queue creation; send0200ee8c copies one item with zero wait and returns boolean; receive0200ef04 waits indefinitely; [0200ef7a](followup/function-0200ef7a.c) accepts a timeout and returns boolean; delete0200f08c forwards to native queue deletion. A pointer-sized queue copies only a pointer. Queue allocation also uses native memory policy. Do not delete a queue while any producer/consumer can access it. A finite receive timeout or an independently verified wakeup protocol is necessary for shutdown; a dropped nonblocking stop message is not a join.

A fixed single-job registry mailbox plus normal-worker polling could avoid another native queue allocation for a bounded prototype, but still needs explicit producer/consumer ownership, bounded sleep period, generation and shutdown rules. Do not turn it into an unbounded busy loop. Full-scene rendering also requires immutable map epochs/pinned readers and device1 XIP coherence; [external XIP review](../ghidra/external-xip-review/report.md) remains the separate contract. A worker queue does not establish transactional flash correctness, render latency, or same-chip read-while-write support.

The bounded task-list exports0200ccaa/0200cf72 are diagnostic traversal facilities, not a proved safe task-name lookup/join API. They are not needed for the fixed registry and should not be used to recover private pointers by walking arbitrary TCB memory.

## Remaining validation

Required next implementation evidence: actual veneer tests at both SP alignments; native creation argument/priority/word-size tests; create failure and worker-completes-before-create-return scheduling models; once-per-boot admission independent of graphics DELETE; registry snapshot/publication memory order; exact-once buffer ownership; status retry/reconnect; and permanent retention of ambiguous/in-progress status after host timeout. Task allocation OOM/assert behavior, idle reaping, interrupts, hardware flash completion and cross-core effects remain unmeasured. No task was created on the glasses in this review.
