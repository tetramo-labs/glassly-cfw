# Native notification / ANCS adapter evidence

Scope: read-only H001Y 1.0.3.127 segment 3 at XIP base `0x041eb020`, SHA256 `81346c77371a91544dd0b79dd7f108f553f60d5459a3e7e797ebffbebbda5ba8`. Function exports beside this report contain disassembly witnesses as well as decompiler output. Exports used the existing project with `-readOnly -noanalysis`. No device commands, notification actions, runtime changes, or subscription changes were performed. This establishes static producer and ownership facts, not notification parity on hardware.

Follow-up: [outgoing action and pre-stock hook proof](action-and-hook.md) closes the B-core synchronous RPC, copy-before-return, service-task consumer, and exact incoming callsite questions. This report retains the original producer findings; the follow-up supersedes its earlier outgoing-boundary limitation.

## Finding

Stock firmware has two distinct paths: companion-delivered GM notification JSON on the display worker, and true ANCS Bluetooth source/data events on the app worker. The existing Android capture demonstrates service-5 setting exchanges only. It does not demonstrate ANCS or message delivery. `runtime/portable/notifications.c` can consume bounded ANCS records, but its native adapter remains unimplemented.

## Android companion and GM path

JADX `analysis/jadx/base/sources/notification/listener/service/NotificationListener.java` extends Android `NotificationListenerService`. Posted and removed callbacks pass a removal flag to `handleNotification`. Posts are deduplicated by package/title/text for five seconds. An explicit package-targeted, permission-protected broadcast carries package, Android notification ID, title, message, removal flag, picture-presence flag, and reply availability. `NotificationReceiver.java` exposes these through Flutter's event channel. `NotificationListenerServicePlugin.java` uses `x-slayer/notifications_channel` / `x-slayer/notifications_event`; `sendReply` resolves a cached action by integer Android notification ID, and `models/Action.java` supplies RemoteInput results to PendingIntent. These are Android quick replies, not ANCS positive/negative actions or ANCS UIDs.

`flutter-strings.txt` contains app-side notification filters/readout/serialization-related names. Flutter machine-code serialization was not reconstructed in this pass; string names alone do not prove the complete GM wire schema or removal forwarding.

Native service 5 callback is `0x042e522c` (initializer `../dispatch/function-042e8114.c`, callback-table offset `0x48`; general dispatch indexes `0x34 + service*4`). ABI is command, TLV-list pointer, event pointer, response-pointer output, in a0..a3. Command 1 passes the owned request pointer to `0x0425add2(0, 0x5c, request, 4)` and returns STATUS 0 without checking enqueue outcome. Commands 3/4 accept type-8 length-one bytes and write configuration keys `0x5400`/`0x5401`; exact user-facing meanings are not inferred here. Other commands return STATUS 2.

Display queue constructor `0x0425a9dc` stores the request pointer in a 12-byte class-0 envelope (event u16 +4, length 4 at +6, pointer +8). This copies a pointer, not the TLV data. `0x0425abe8` owns failed-enqueue disposal; display worker `0x0425b38a` loads that pointer and passes it to `0x04262c8e`. That routine calls `0x042616dc`, which **loads the first word of the request (the next-node link)** before tail-calling `0x042a7650`. Thus the JSON consumer is reached through the next TLV node, not an assumed first/only JSON TLV. The first-node meaning remains unresolved.

`0x042a7650` consumes type 5 with 24-bit length and value pointer, parses JSON descriptor keys `id`, `type`, `a`, `ts`, `ti`, `c`, `pkg_name`, and stores the JSON through `0x0429f310(2, data, length & 0xffff, timestamp)`. Exact key literals are at `0435f598`, `0435ea6c`, `04374878`, `0435ad3c`, `0437628c`, `0435d950`, `04362e28`. Their presence does not establish all field semantics. A read-state/duplicate branch can suppress storage. At display dispatch completion `0x04262c8e` invokes `0x042e85ae(event, &request)`; for event `0x5c` this calls TLV release `0x042eff8e`. A passive copy must happen before that cleanup, never retain native TLV pointers, and preserve stock dispatch.

`captured-service5.json` is the service-5 subset of `analysis/protocol/general-session/normal-frames.json`: two cmd-3/type-8/value-0 requests and two STATUS-0 responses. No cmd-1 notification body occurs in this examined subset.

## True ANCS events and layouts

`0x042127a4` registers `0x04217546` under app topic 0 and lower Bluetooth callback `0x04212cea` through `0x04316aca`. The latter registration is a **single global callback replacement**, and may synchronously emit current connection state. It is not an additive notification API.

App callback ABI: `callback(event_u16, payload, payload_length_u16)`. `0x04217546` routes:

| Event | Stock target | Meaning established by code |
|---|---|---|
| `0x258` | `0x042117aa` | peer/state event, state u32 at +8; state 3 initiates connected processing, <2 clears pending peer requests |
| `0x259` | `0x04211abe` | control completion, drains pending ANCS requests |
| `0x25a` | `0x04211af4` | notification source |
| `0x25b` | `0x04211c34` | completed data-source attributes |

Source payload minimum 14 bytes: peer address bytes 0..5; event ID +6; flags +7; category +8; count +9; UID little-endian bytes +10..13. Bytes +6..13 are exactly the portable core's eight-byte `mm_notifications_source` record. Stock filters flag mask `0x04` in one mode, suppresses automatic attribute requests during its connection grace state, and only requests attributes for event IDs 0/1. A pre-stock observer preserves removal/pre-existing source records even when stock does not fetch their attributes. The stock test is flags & 0x04 (bit index 2, the pre-existing flag); it is not bit index 4. One earlier lower callback filter `0x04211654` can suppress source events before app enqueue; this pass does not bypass that policy.

Attribute event descriptor is 16 bytes (last two bytes padding/unspecified; semantic fields occupy 14 bytes): peer address 0..5; command byte +6; byte +7 unspecified; 32-bit body pointer +8; u16 length +12. Command 0 body starts with four UID bytes then records `[id:u8][length:LE16][value:length]`. Observed IDs: 0 application identifier, 1 title, 2 subtitle, 3 message, 4 message size, 5 date, 6 positive action label, 7 negative action label. Stock display copies are capped to 64/50/50/356/20/32-byte strings as appropriate; a relay should copy bounded original attributes before these presentation truncations. The portable core's 1024-byte attribute maximum is a separate policy; reject longer records rather than silently claim lossless parity.

Command 1 body starts with NUL-terminated application identifier, then `[0][LE16 name length][name]`. `mm_notifications_app_response` expects an additional command byte 1 before that body. Its maximum total length 1024 and bundle-ID maximum 64 must be checked before copying. Do not pass the native descriptor as an ANCS wire buffer.

**Lifetime:** `0x04211c34` frees the body pointer through `0x020099a0` on completion and error paths. `0x04319058(event, &payload, &temporary_owned)` specifically copies the 16-byte event-0x25b descriptor and separately allocates/copies its length-u16 (+12) bytes from pointer +8. It replaces the pointer and marks the descriptor temporary-owned. After app enqueue, `0x043196e0(event, temporary, enqueue_success)` frees just that temporary descriptor on success; on failure it also frees its nested data. This establishes transfer of the copied body to the app handler, not retention of the lower Bluetooth buffer. Source event 0x25a takes the default non-deep-copy path; its inline bytes are copied by the app envelope constructor. Source bytes and the attribute descriptor are borrowed from the app event envelope; the app worker `0x0423590c` frees the envelope after `0x04235770` finishes callbacks. A hook must copy before forwarding to `0x04211c34`; afterward even an unchanged nonzero pointer may be dangling.

The app envelope constructor `0x04235a9c` allocates length+8 and copies the descriptor bytes inline; embedded pointers are not thereby deep-copied. Topic/event/length are at +1/+4/+6 and payload starts +8. The app worker is allocated 4096 bytes of stack (`0x04235ea0` passes 0x400 words to task creation); this is allocation, not measured remaining margin. The app bus supports only two callbacks per topic. `0x04235ffa` appends to a vacant slot, but when both are occupied it shifts out the oldest. `0x04235770` invokes slot 0 then slot 1. A later additive subscriber can run after stock has freed nested ANCS data, and registering can evict stock. Therefore this registration is **not an admitted additive relay interface**. A bounded pre-stock copy/forward wrapper with a separately proved install/detach lifetime is the current candidate, not an implemented hook.

## Action and attribute request boundary

`0x04318ee6(peer6, uid4_pointer, action_byte)` builds exactly 11 stack bytes `[peer6][uid4][action1]`, calls `0x043199d2(0x2c0, payload, 11)`, and returns its a0 result unchanged (assembly `04318f28..04318f36`), despite the decompiler's void prototype. `0x043199d2` rejects disabled/busy global Bluetooth states with 11 and maps lower enqueue failure to 11; zero means lower dispatch accepted, not remote action completed. Its actual a1/a2 payload arguments are preserved into `0x04316d00` despite the inferred one-argument decompilation. `0x04316d00` is a tail trampoline to `0x0434b3a4`; the [follow-up](action-and-hook.md) traces its synchronous B-core RPC and proves a successful action copies UID/action into an owned message before acknowledgment. A new caller still needs peer/UID validation, task/ordering integration, and native OOM/timeout handling policy.

Attribute wrapper `0x04318e32` sends command `0x2be`: peer6, UID4, an attribute-spec pointer at +12, count byte +16, 20-byte outer request. App-name wrapper `0x04318e8e` sends `0x2bf`: peer6, identifier pointer +8, identifier length byte +12, attribute pointer +16, attribute count byte +20, 24-byte outer request. These contain borrowed pointers; the follow-up proves B-core copies their bounded contents into owned messages before replying (attribute spec <=14 bytes, app identifier <=39 bytes, app-attribute spec <=1 byte).

Existing app ANCS queue drain `0x04211494` serializes pending request types 0 (notification attributes), 1 (app attributes), 2 (action). Nodes are 36 bytes; type +8, peer +12, action UID +18 and action byte +22 for type 2. `0x042117aa` clears queued peer requests on disconnected states; `0x042113ce` finds per-peer state. The follow-up locates the callable synchronous action RPC, but no public app-worker queue submission API or complete UID-to-peer lifetime policy is provided by it. The portable action callback receives UID/action only: an adapter must retain validated peer association, invalidate on disconnect, reject stale/ambiguous UIDs, and preserve stock request ordering. Android IDs must not be substituted.

## SDK and integration gaps

Pinned SDK commit `171098bff25934a534a49f95b88df58fbed404c7`, `GlassSDK/include/gm_plugin_extensions.h`, exposes SYSTEM_EVENTS extension 5 with CALL_UI type 1, timestamp, active boolean. It explicitly excludes caller identity/phone number, borrows events on the display task, replaces the subscription, and revokes before unload. This is call-overlay state, not message/ANCS delivery. Reviewed SDK headers expose no message-content or ANCS subscription contract.

Before native integration: prove pre-stock hook installation and producer quiescence; serialize producer/control/timer access to one core; select a bounded owned-copy queue and backpressure; prove timer cancellation and retryable teardown; route output through an actual MemoMind service rather than treating G2 field-125 framing as a native channel; implement peer-scoped action validation. App-worker data and display-worker lifetime must not be joined by retaining pointers to an LVGL owner. The ANCS data handler itself allocates temporary buffers and can assert through native allocation paths; the relay must add only bounded work and preserve stock failure behavior.

Search boundary: existing stock segment-3 project, source/attribute/action call chains above, captured Android notification plugin, selected libapp strings, public SDK headers and historical service-5 frames. No iPhone/ANCS session, notification permission change, posted test notification, action execution, or live ownership/teardown test was performed. Full producer discovery/connection subscriptions in lower Bluetooth firmware and Dart GM serialization remain incomplete. API/code presence is not a hardware parity pass.
